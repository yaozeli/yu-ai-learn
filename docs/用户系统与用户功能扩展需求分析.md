# 鱼皮 AI 闯关学习小程序

# 用户系统与用户功能扩展需求分析

## 1. 文档说明

### 1.1 文档目的

本文档用于定义现有 AI 闯关学习小程序的用户系统及用户相关功能扩展需求，作为后续方案设计、开发拆批、测试和验收的依据。

本文档只描述产品需求和验收要求，不定义具体技术架构、数据库表结构、接口实现方式或页面代码方案。

### 1.2 本次确认实现范围

1. 微信静默登录与用户身份识别。
2. 使用 JWT 进行后续接口鉴权。
3. 获取用户基础信息，包括微信 `openid`、昵称和头像。
4. 个人中心基础页面。
5. 闯关历史记录。
6. 答题记录和学习报告历史。
7. 错题本与错题复习状态。
8. 将现有闯关流程与用户数据关联。

### 1.3 本次暂不实现的范围

1. 学习数据分析，包括学习趋势、热力图和知识点掌握度。
2. 成长体系，包括 XP、金币、等级、徽章和连续学习天数。
3. 设置、隐私和稳定性完善，包括学习提醒、每日打卡提醒、音效动效和隐私设置。
4. 多源输入：PDF、Word、网页链接和视频链接解析。
5. RAG 私有知识库。
6. 好友系统、邀请裂变、排行榜和双人 PK。
7. VIP 会员、充值、按量付费、支付系统和企业 B2B 套餐。
8. 生图、语音、数字人等多模态功能。

上述功能保留在后续产品规划中，不纳入当前开发批次和本次版本验收。

### 1.4 已确认的产品和数据约束

1. 数据库统一采用 MySQL，开发和生产环境均不切换为 SQLite。
2. 采用微信静默登录建立用户身份，使用 JWT 进行后续接口鉴权。
3. 微信登录只保存微信 `openid`、用户昵称和用户头像，不采集手机号等额外个人信息。
4. 用户数据必须按用户身份隔离，用户只能访问自己的学习数据。
5. 前后端接口可以统一采用 `{ code, message, data }` 响应格式。
6. 现有核心 AI 闯关流程继续保留，并在本次扩展中接入用户数据。
7. 前端继续遵循现有原型的视觉风格和页面结构。

## 2. 产品目标

1. 用户打开小程序后能够完成微信静默登录，并在后续访问中保持登录状态。
2. 用户完成闯关后，系统能够保存本次学习过程、答题结果和复盘报告。
3. 用户能够在个人中心查看自己的基础资料和历史学习内容。
4. 用户能够查看、重新练习和管理错题。
5. 用户能够安全退出登录。
6. 用户在网络异常、登录失效或数据加载失败时能够获得明确反馈。

## 3. 用户角色

### 3.1 普通登录用户

普通登录用户可以：

1. 使用微信静默登录小程序。
2. 查看自己的基础资料。
3. 创建和完成 AI 闯关。
4. 查看自己的闯关历史、报告和答题记录。
5. 查看和复习自己的错题。
6. 退出当前登录状态。

### 3.2 未登录用户

1. 未登录用户可以打开小程序并看到首页。
2. 未登录用户可以输入学习主题。
3. 未登录用户是否可以在登录前生成题库，待方案设计前确认。
4. 未登录用户不能访问个人中心、历史记录和错题本。
5. 静默登录完成后，应尽可能保留用户当前输入内容，避免重复输入。

## 4. 需求批次与优先级

开发按用户价值、数据依赖和业务风险拆分为以下批次，前一批次通过验收后再进入下一批次。

| 批次    | 优先级 | 批次名称           | 目标               | 主要依赖                |
| ----- | --- | -------------- | ---------------- | ------------------- |
| 第 1 批 | P0  | 微信静默登录与 JWT 会话 | 建立可靠的用户身份体系      | 微信 AppID、登录配置、MySQL |
| 第 2 批 | P0  | 用户资料与基础个人中心    | 用户能够查看自己的基础身份信息  | 第 1 批               |
| 第 3 批 | P0  | 闯关数据持久化        | 保存闯关、答题和报告数据     | 第 1 批、第 2 批         |
| 第 4 批 | P1  | 闯关历史与报告历史      | 支持用户回看学习过程       | 第 3 批               |
| 第 5 批 | P1  | 错题本与复习         | 形成错题沉淀和复习闭环      | 第 3 批、第 4 批         |
| 后续    | P1  | 学习数据分析         | 展示学习趋势和知识点掌握情况   | 第 3 批至第 5 批         |

| 后续    | P1  | 设置与隐私          | 完成提醒、隐私和更多用户设置   | 前述批次                |

## 5. 分批需求详情

### 5.1 第 1 批：微信静默登录与 JWT 会话

#### 功能需求

1. 小程序能够发起微信静默登录，不额外要求用户授权手机号等信息。
2. 后端能够根据微信登录凭证识别用户，并建立或复用用户账户。
3. 首次登录时创建用户账户。
4. 已登录用户再次登录时复用原有账户，不重复创建用户。
5. 系统向前端返回 JWT 登录态凭证。
6. 前端保存 JWT，并在后续受保护请求中携带 JWT。
7. JWT 失效时，前端清理失效凭证并重新发起静默登录。
8. 退出登录后，前端清理本地登录态。
9. 登录失败、微信接口异常和网络异常时展示明确提示。
10. 开发环境提供不依赖真实微信接口的测试登录方式；该方式不得在生产环境开放。

#### 保存的数据

1. `openid`。
2. 微信昵称。
3. 微信头像。
4. 系统生成的用户标识。
5. 创建时间、更新时间和最近登录时间。

不保存手机号、微信好友关系、微信号或其他未确认的个人信息。

#### 验收标准

1. 新用户首次登录后能够建立账户。
2. 同一微信用户重复登录不会产生重复账户。
3. 登录后访问受保护功能能够通过身份校验。
4. 用户无法使用其他用户的 JWT 访问数据。
5. JWT 失效后能够重新建立登录态。
6. 退出登录后访问受保护功能会重新要求登录。
7. 生产配置不会暴露开发环境 mock 登录入口。

### 5.2 第 2 批：用户资料与基础个人中心

#### 功能需求

1. 增加“我的”个人中心入口。
2. 展示当前用户头像和昵称。
3. 提供“我的闯关记录”入口。
4. 提供“错题本”入口。
5. 对未登录状态展示登录引导，不展示其他用户或虚构数据。
6. 用户信息加载失败时展示可重试状态。
7. 本次默认只支持查看微信昵称和头像，是否允许修改待后续确认。

#### 验收标准

1. 个人中心展示的用户资料属于当前登录用户。
2. 首次登录、无学习记录和数据加载失败时都有合理空状态。
3. 已纳入范围的个人中心入口均可正常进入。
4. 用户退出登录后，个人中心不再展示受保护的个人数据。
5. 页面结构和视觉层级遵循原型 2 的个人中心页面。

### 5.3 第 3 批：闯关数据持久化

#### 功能需求

1. 每次生成题库时记录所属用户。
2. 保存题库基本信息，包括主题、标题、摘要、来源类型和生成时间。
3. 保存题目基本信息及知识点标签。
4. 用户开始闯关后能够记录本次闯关状态。
5. 用户每道题提交后记录所选答案、是否正确和答题耗时。
6. 用户完成全部题目后保存本次闯关结果。
7. 保存正确题数、题目总数、正确率和总耗时。
8. 保存 AI 生成的复盘报告。
9. 错题与用户和具体题目关联。
10. 最后一题答题记录必须进入最终统计和复盘报告。
11. 生成题库成功但用户中途退出时，是否保存未完成状态待方案设计确认。
12. 数据保存失败时提示用户，并明确哪些数据仍保留在本地。

#### 核心业务规则

1. 后端不能信任前端传入的用户标识。
2. 正确率和完成状态以服务端可验证的数据为准。
3. 用户只能读取和修改自己的闯关数据。
4. 同一答题记录不能被重复计入统计。
5. 删除或清理数据时不能影响其他用户。

#### 验收标准

1. 用户完成一次闯关后，刷新或重新进入小程序仍能查到该记录。
2. 统计结果包含全部题目，特别是最后一道题。
3. 报告中的正确率与答题记录计算结果一致。
4. 两个用户的数据完全隔离。
5. AI 生成失败时不会产生虚假的完成记录。

### 5.4 第 4 批：闯关历史与报告历史

#### 功能需求

1. 提供闯关历史列表。
2. 展示学习主题或闯关标题。
3. 展示完成时间、正确率、答对题数和总题数。
4. 展示学习状态，例如已完成或未完成。
5. 按时间倒序展示最近记录。
6. 支持分页或加载更多，不能一次性加载无限数据。
7. 点击历史记录可以查看详情。
8. 详情页展示题目答题情况、正确答案、知识讲解和本次报告。
9. 没有历史记录时展示空状态和返回首页入口。
10. 历史记录加载失败时展示重试入口。

#### 验收标准

1. 用户只能看到自己的闯关历史。
2. 列表排序稳定，最新记录优先。
3. 列表和详情数据一致。
4. 分页加载不会出现重复记录或漏记录。
5. 删除、隐藏或清理记录暂不实现，除非后续确认。
6. 页面遵循原型 2 的产品风格。

### 5.5 第 5 批：错题本与复习

#### 功能需求

1. 用户答错题目后自动加入错题本。
2. 错题按知识主题或知识点分组展示。
3. 展示题干、所属主题、最近答错时间和复习建议。
4. 错题详情展示选项、用户答案、正确答案和知识讲解。
5. 支持从错题进入重新挑战。
6. 用户重新答对后更新错题掌握状态。
7. 用户多次答错时保留复习记录，但不生成无意义的重复条目。
8. 展示待复习题数量。
9. 根据答错时间提供复习时间提示。
10. 支持“旧识重温”入口；完整宝藏关卡玩法暂不实现。
11. 错题数据必须按用户隔离。
12. 错题加载失败时展示重试入口。

#### 复习规则边界

1. 本次先实现基于答错时间的复习建议。
2. 复习建议需要具备可解释的时间规则。
3. 复杂的个性化记忆模型暂不实现。
4. 自动推送通知本次不实现。

#### 验收标准

1. 答错题目能够进入当前用户的错题本。
2. 用户重新答对后，题目状态能够更新。
3. 错题列表按主题分组且数量准确。
4. 重复答错同一题不会造成不可控的数据膨胀。
5. 用户无法查看其他用户的错题。
6. 页面遵循原型 2 的错题本页面。

## 6. 页面范围

本次扩展涉及以下用户相关页面或页面状态：

1. 微信静默登录及登录失效后的登录引导。
2. 个人中心。
3. 闯关历史列表。
4. 闯关历史详情。
5. 错题本。
6. 错题详情或复习闯关入口。
7. 用户资料查看。
8. 现有首页、闯关页、结算页和报告页的登录态及数据保存状态。

页面视觉和交互要求：

1. 遵循原型 1、原型 2 的颜色、卡片、圆角、按钮和信息层级。
2. 不自行加入原型中未定义的复杂视觉风格。
3. 页面需要具备加载中、空数据、失败和重试等必要状态。
4. 不因增加用户功能而破坏首页到闯关再到报告的核心路径。
5. 移动端文字、按钮和数据卡片不得出现重叠或溢出。

## 7. 非功能需求

### 7.1 数据安全

1. 用户数据必须进行身份校验和归属校验。
2. 不允许通过修改请求参数读取其他用户数据。
3. 不在客户端信任用户传入的正确率、完成状态和用户标识。
4. 不保存未获用户确认的额外个人信息。
5. 生产环境不得启用 mock 登录。
6. 敏感配置不得写入代码仓库。

### 7.2 一致性和可靠性

1. 关键写操作需要支持重复请求保护。
2. 闯关完成和报告生成之间不能产生明显的数据不一致。
3. AI 生成失败时不能保存为成功完成。
4. 网络重试不能导致重复答题记录。
5. 数据库异常需要返回用户可理解的提示，并记录服务端诊断信息。

### 7.3 性能

1. 历史列表和错题列表需要支持分页或限制单次返回数量。
2. 个人中心首屏优先返回基础信息。
3. AI 生成过程继续展示明确的加载状态。

### 7.4 可测试性

1. 后端用户登录、JWT 身份校验和数据隔离必须有自动化测试。
2. 闯关保存、最后一道题统计和报告生成必须有回归测试。
3. 错题生成和复习状态必须有单元测试。
4. 关键 API 需要有接口集成测试。
5. 前端至少验证静默登录、登录态、个人中心、闯关完成和历史记录等关键路径。
6. 后端功能按照 TDD 方式开发，先编写失败测试，再实现功能。

## 9. 方案设计前需要人工确认的信息

### 9.1 微信与环境信息

1. 微信小程序 AppID。
2. 是否已经注册并认证微信小程序账号。
3. 是否已经配置服务器域名和 request 合法域名。
4. 开发、测试、生产环境是否使用不同的 AppID 或域名。
5. MySQL 版本、字符集和时区。
6. 后端部署环境，例如云服务器或容器平台。
7. 是否已有 HTTPS 证书和域名。

不要在聊天中直接发送数据库密码、微信 AppSecret 或其他长期密钥，后续通过本地 `.env` 或安全配置方式提供。

### 9.2 登录策略

1. 静默登录失败时，是否允许用户继续使用不保存历史的临时体验？ **不允许**
2. 是否允许未登录用户先生成题库，再在开始答题前登录？ **不允许**
3. 用户昵称和头像是否允许修改？ **允许**
4. 是否需要提供账号注销功能？ **暂时不需要**
5. JWT 有效期和刷新策略由后续方案设计提出。

### 9.3 闯关与数据保存策略

1. 题库是在生成成功时保存，还是用户开始答题时保存？ **生成成功时保存**
2. 中途退出的闯关是否保存为未完成记录？ **是**
3. 是否允许用户继续未完成闯关？ **允许**
4. 历史记录是否允许删除？ **暂时不考虑**
5. 是否需要保存每次题目生成的完整题库内容？ **不需要**
6. 报告生成失败时，是否允许稍后重新生成？ **允许**

### 9.4 错题与复习口径

1. 同一道题重复答错是否只保留一条错题？ **是**
2. 重新答对后错题是标记已掌握、隐藏，还是移出错题本？ **移除**
3. 是否需要微信订阅消息推送复习提醒；本次默认不实现自动推送。

## 10. 后续流程

1. 由人工确认本需求分析文档。
2. 根据确认结果补充或修订需求。
3. 人工确认无误后，单独编写技术方案设计文档。
4. 技术方案确认后，按批次从第 1 批开始开发。
5. 每一批次先补充或调整测试，再实现后端和前端功能。
6. 每一批次完成后进行接口测试、构建验证和人工验收。
7. 未确认的产品规则不进入正式实现。
